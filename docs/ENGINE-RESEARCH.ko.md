## 현재 엔진과 남은 문제

현재 엔진은 NVOFA로 양방향 움직임을 추정합니다. 분석 영상의 긴 변은 최대 1920픽셀이며, 기본 설정은 Grid 4 우선·Medium입니다. Cost Map과 Temporal Hints는 기본적으로 꺼져 있고, 호환되는 연속 프레임 쌍에서는 공유 자원과 세션을 재사용합니다.

`motion.hlsl`은 일부 반복 무늬의 잘못된 대응을 보정한 뒤, 반복 횟수를 제한한 Newton 방식으로 중간 프레임에서 원본을 찾는 역좌표를 계산합니다. 앞뒤 원본의 후보 위치에 신뢰도를 부여하고, 원본 해상도의 Y/UV 값을 읽어 합성합니다. 원본 P010과 생성 프레임은 기존 10bit 경로를 유지합니다. 이미 여러 보간 배수와 중간 시점을 지원하므로, 오래된 문서의 ‘×2 전용’이나 ‘8bit 전용’ 설명을 현재 제약으로 보면 안 됩니다.

남은 문제는 다음 세 단계로 나누어 봐야 합니다.

1. **원본 간 대응 관계:** 반복 무늬나 흐름 격자보다 작은 물체에는 잘못된 움직임이 배정될 수 있습니다. 앞뒤 방향의 추정이 서로 일치해도, 반복 무늬의 다른 위치를 가리킨 것일 수 있습니다.
2. **가시성 판단:** 한 원본에서 보이는 표면이 다른 원본에서는 가려질 수 있습니다. 따라서 앞뒤 색이 맞지 않는다는 이유만으로 그 표면이 중간 시점에서도 잘못된 후보라고 단정할 수 없습니다. 반대로 색과 움직임이 맞더라도, 앞쪽 물체 대신 가려진 배경을 선택할 수 있습니다.
3. **영상 재구성:** 흐름을 보간하면서 앞쪽 물체와 배경의 움직임이 섞일 수 있습니다. 역좌표의 수치 오차가 매우 작아도 선택한 표면과 신뢰도가 틀릴 수 있습니다. 역좌표 맵을 확대할 때 서로 무관한 위치를 평균 내지 않도록 하는 기존 처리는 유지했습니다.

이전의 좁은 틈 조사에서는 실패한 일부 픽셀의 역좌표 오차가 매우 작았지만, 앞뒤 원본의 절대 신뢰도는 모두 거의 0이었습니다. 그런데 상대 비율로 정규화하면서 잘못된 후보 하나가 출력의 거의 전부를 차지했습니다. 이는 해당 픽셀에서 Newton 반복을 늘리는 것만으로 해결하기 어렵다는 근거입니다. 모든 영상의 문제가 같은 원인이라는 뜻은 아닙니다. 신뢰도가 낮을 때 원본을 반복하거나 앞뒤 원본을 전역적으로 섞는 방식도 빠진 가시성 정보를 복원하지 못합니다.

이미 채택한 고정 가는 선 보호는 별도의 처리입니다. 조준선 개선이 움직이는 가는 물체나 새로 드러나는 배경의 해결을 뜻하지는 않습니다. 이전 Grid·Preset 변경, 평탄 배경 대체, 주변 움직임의 연장, Newton 시작점 추가 실험은 [가는 고정선 시험 기록](THIN-OVERLAY-TRIAL.md), [흐름 설정 시험 기록](FLOW-PROFILE-TRIAL.md), 로컬 인수인계 자료에 정리돼 있습니다. 기각한 실험을 성공한 개선으로 간주하지 않았습니다.

## 구현한 두 후보

### surface1 — 같은 움직임에 속한 주변 표본으로 신뢰도 계산

기존 `warpReliability`는 분석 영상 기준 4픽셀 간격으로 배치한 3×3 표본의 색 차이를 평가합니다. 물체 경계에서는 앞쪽 물체와 배경이 같은 패치에 들어와, 올바른 원본 후보도 이웃 표본 때문에 낮은 점수를 받을 수 있다는 가설을 세웠습니다.

후보는 각 표본의 움직임이 중심 표본과 얼마나 같은지에 따라 가중치를 부여합니다. 유효 표본이 최소 4개에 해당할 때만 새 평가를 사용하고, 부족하면 기존 평가를 유지합니다. 역변환 신뢰도의 색 차이 평가만 바꿨으며, 움직임 보정·Newton 계산·마스크·프레임 전달·출력 스케줄링은 v0.4.8과 동일합니다.

이 방식은 완전한 가시성 모델이 아닙니다. 잘못됐지만 주변과 일관된 움직임을 과신할 가능성도 있습니다. 따라서 정답 영상·실제 영상·성능 검증을 통과하기 전까지 제품 셰이더에 넣지 않았습니다. 실험 셰이더, 준비 스크립트, 새로 빌드한 기준 실행 파일은 `build/engine-research-20261013/`에 보존했습니다.

### stretch1 — 면적 변화가 작아도 심한 방향별 늘어남 감지

두 번째 후보는 기존 패치 평가를 유지하면서 기하학적 감점만 바꿨습니다. 기존 행렬식은 면적 변화를 측정합니다. 예를 들어 `diag(4, 0.25)`는 가로로 크게 늘어나고 세로로 줄어도 면적은 그대로입니다.

후보는 중간 시점 변환의 Jacobian에서 가장 큰 특이값도 계산해, 특정 방향의 심한 늘어남을 평가합니다. 기존 색 불일치 조건과 1.5 임계값은 유지했습니다. 단순 평행 이동과 색이 잘 맞는 패치에는 기존 가중치를 유지합니다. 다만 이 방식도 깊이를 추정하거나, 가려진 표면의 잘못된 대응을 올바르게 바꾸지는 못하므로 동일한 회귀 검증이 필요합니다.

## 1차 검증 결과

**두 후보 모두 채택하지 않았습니다.** `src/`와 `include/`의 제품 코드는 v0.4.8과 같습니다. 이번 작업의 결과물은 정답 기반 비교 도구와 연구 기록이며, 새 필터 배포본은 없습니다.

새로 빌드한 기준 버전은 CTest 19개를 모두 통과했습니다. 기존 8장면 시험도 ×2·×3·×4·×5에서 통과했고, 중간 프레임의 움직임 위치와 원본 보존을 확인했습니다. 새 비교 도구는 닫히는 틈과 단순 평행 이동의 ×2·×5, 총 4조건에서 기준 엔진끼리 결과가 정확히 일치했습니다.

기준 빌드는 `gpu_p010_conversion` 검사도 통과했습니다. 1024개 코드값 전체, 잘라내기·UV 처리, 디코더 자원 재사용, 상태·탐색, 움직이는 영상의 ×5·×10 정밀도, 4K ×10의 큐 방식과 완료 대기 방식 간 픽셀 일치를 확인했습니다. 이는 기준 엔진 검사이며, 실제 플레이어의 HDR 또는 HW↔SW 전환을 이번에 새로 시험했다는 뜻은 아닙니다.

| 열리는 틈 ×5 / 드러나는 배경 | 33.8096 | 34.3471 | 34.9765 |
| 움직이는 가는 물체 ×5 / 세부 영역 | 1182.3649 | 1303.8893 | 1181.4401 |
| 밝은 물체 ×5 / 세부 영역 | 117.5534 | 136.4673 | 116.0616 |
| 곡선 물체의 가림 ×5 / 경계 | 28.2047 | 33.4515 | 27.9245 |
| 고정 가는 선 ×5 / 세부 영역 | 176.3245 | 176.3559 | 176.3245 |

`surface1`은 움직이는 세부 영역의 품질을 크게 악화시켰습니다. 평가할 주변 표본을 제한한다고 움직임 추정 자체가 올바르게 되는 것은 아니었습니다.

`stretch1`은 일부 경계에서 소폭 좋아졌지만, 드러나는 배경의 오차가 ×2에서 약 6.6%, ×5에서 약 3.5% 증가했습니다. 일부 영역의 작은 이득만으로 이 회귀를 감수할 근거는 부족합니다.

두 후보 모두 원본 픽셀·시간·프레임 쌍의 처리 판단은 유지했고, 단순 평행 이동 결과도 변하지 않았습니다. 그러나 기능적 일치만으로 화질 검증을 통과한 것은 아닙니다.

### 실제 영상과 비교

실제 영상 6구간을 비교했습니다. 보고된 움직이는 물체와 고정선 애니메이션, 실사의 좁은 틈, 추가 애니메이션 2구간, 4K 실사의 원본 프레임 제외 시험을 포함하며 **엔진별 입력 257쌍**입니다.

두 후보 모두 기준 버전의 타임스탬프와 프레임 쌍 처리 판단을 유지했습니다. NV12 원본은 바이트 단위로 정확히 같았습니다. P010 원본도 비교 도구가 출력하는 상위 바이트 정밀도에서는 같았지만, 이 비교 자체가 전체 10bit를 새로 검증한 것은 아닙니다.

문제 영역을 확대해 확인한 결과, 움직이는 경계의 너덜거림과 좁은 틈 배경의 손상은 남았습니다. 변화는 작았고 뚜렷한 시각적 해결은 확인하지 못했습니다. 고정선의 잔여 결함도 남아 있습니다. 이 구간들에는 실제 중간 시점의 정답 프레임이 없으므로, 단순한 출력 차이를 개선 점수로 보고하지 않았습니다.

원본 프레임 31개를 제외한 뒤 복원해 비교한 실사 시험에서는 전체 화면의 휘도 MSE가 다음과 같았습니다.

- 전체 화면: **95.0940 → 95.1360(surface1) / 95.3670(stretch1)**
- 지정 관심 영역: **137.3538 → 137.4279 / 137.8144**

모두 소폭 나빠졌습니다. 이 시험은 원본을 한 장씩 건너뛰어 입력하므로 일반 재생보다 입력 간격이 두 배입니다. 입력 전달 형식은 P010이지만, 위 진단 지표는 8bit 휘도 기준입니다.

재현 자료는 `build/engine-research-20261013/` 아래의 `baseline-ctest.log`, `baseline-layers.log`, `baseline-p010.log`, `harness-self-check`, `surface1-analytic`, `stretch1-analytic`, `real-baseline-surface1-stretch1`에 있습니다. 원본 이미지·영상 경로·로그는 공개 저장소에 포함하지 않았습니다. 두 후보는 앞선 품질 기준에서 탈락했으므로 제품 연결이나 설치로 진행하지 않았고, 후보의 HDR·GPU 선택·실제 재생 검증을 완료했다고 주장하지 않습니다.

### 성능 측정과 한계

시험 장비는 **RTX 5090, 드라이버 617.42**입니다. 첫 번째 실제 영상 측정은 실행당 7쌍을 측정했는데, 일부 4K ×2 실행의 평균이 약 17ms, 다른 실행은 약 3.8ms로 편차가 컸습니다. 원인은 확정하지 못했으며, 이 결과로 후보의 속도 이득을 주장하지 않습니다. 원래 기록도 `performance/`에 보존했습니다.

두 번째 시험에서는 NV12 이미지 8개를 미리 올리고 움직임을 순환시켰습니다. 준비 실행 8쌍 이후 64쌍을 측정했으며, 측정 중에는 프레임 파일 출력이나 중간 프레임별 CPU 읽기를 하지 않았습니다. GPU 작업 완료까지의 시간을 포함했습니다.

각 해상도·배수에서 기준 → surface1 → stretch1 → stretch1 → surface1 → 기준 순서로 실행했습니다. 아래 값은 두 번 실행한 결과의 범위이며, 해당 쌍의 모든 중간 프레임을 포함한 **입력 한 쌍당 처리 시간(ms)**입니다.

| 해상도·배수 | v0.4.8 | surface1 | stretch1 |
|---|---:|---:|---:|
| 1920×1080 / ×2 | 2.689–2.986 | 2.775–2.804 | 2.691–2.915 |
| 1920×1080 / ×5 | 3.425–3.499 | 3.688–3.738 | 3.409–3.464 |
| 3840×2160 / ×2 | 3.726–3.793 | 3.764–4.126 | 3.698–3.779 |
| 3840×2160 / ×5 | 5.226–5.527 | 5.144–5.555 | 4.848–5.326 |

이번 1080p ×5 시험에서는 `surface1`이 느렸습니다. 다른 조건은 범위가 겹치거나 실행 순서에 따른 편차가 있어, 전반적으로 더 빠른 후보라고 판단할 수 없습니다.

이 수치는 합성 NV12 영상의 엔진 처리 측정입니다. 디코딩·P010 재생·화면 드롭이나 렌더러와 GPU를 공유할 때의 성능을 보장하지 않습니다. GPU 클럭과 다른 데스크톱 활동은 고정하지 않았습니다. 두 후보의 코드에는 추가 텍스처 할당이 없지만, 프로세스 전체 VRAM 사용량은 측정하지 않았습니다. 로그와 측정용 소스·빌드 스크립트는 `performance-drained/`와 로컬 연구 폴더에 있습니다.

## 비교 도구와 검증 기준

`tools/compare-occlusion.py`는 두 엔진과 독립적으로 연속 시간의 도형을 직접 그려 정답 영상을 만듭니다. 열리고 닫히는 틈, 움직이는 가는 물체, 작고 밝은 물체, 반복 배경, 곡선 가림 물체, 단순 평행 이동, 고정선을 포함합니다.

×2·×5에서 원본, 모든 출력 타임스탬프, 프레임 쌍 처리 판단을 확인하고, 경계·보이는 배경·움직이는 세부 영역의 MSE를 따로 계산합니다. 앞뒤 원본의 평균을 정답으로 사용하지 않습니다. 후보 MSE가 `기준 MSE × 1.03 + 0.01`을 넘으면 회귀로 표시합니다. 이 기준을 통과하는 것만으로 화질 개선이 입증되지는 않습니다.

도구는 GPU 실행 전에 플레이어와 다른 시험 프로세스를 확인합니다. 테스트용 `LOCALAPPDATA`를 분리하고, 실행 파일 해시를 기록하며, `build/` 아래에 새로 만든 폴더에만 결과를 씁니다. 선택한 표본은 남기고 자신이 생성한 임시 원시 출력만 정리합니다. `--keep-raw`를 지정하면 원시 출력도 보존합니다.

```powershell
python tools/compare-occlusion.py --baseline <baseline-video_x2_repro.exe> --candidate <candidate-video_x2_repro.exe> --output build/new-occlusion-comparison
```

## 다음 실행 계획

후속 후보는 다음 순서로 검증합니다.

1. **정답이 있는 합성 시험:** 독립적인 정답 영상과 기존 8장면·다중 시점 시험을 사용합니다. 전체 평균이 좋아져도 작은 관심 영역의 악화를 따로 확인합니다.
2. **실제 문제 영상과 다른 영상:** 보고된 구간과 추가 애니·실사에서 확대 이미지와 시간에 따른 움직임을 확인합니다. 정답 중간 프레임이 없는 구간에서는 달라진 픽셀을 객관적인 개선으로 간주하지 않습니다. 사적인 이미지는 로컬에만 둡니다.
3. **실제 원본 프레임 제외 시험:** 디코딩한 원본을 정답으로 비교합니다. 일반 재생보다 입력 간격이 두 배임을 명시하고 장면 전환·원본 반복 판단도 함께 기록합니다.
4. **성능·메모리:** 1080p·4K, ×2·높은 배수에서 순차 반복 측정합니다. GPU 완료까지의 시간과 메모리를 확인하며, 프레임 쌍 처리량을 플레이어·화면 FPS와 구분합니다.
5. **통합 검증:** 앞선 기준을 통과한 후보만 P010 정밀도, HDR 신호 전달, HW↔SW·GPU 선택, 공유 컨텍스트의 자원 수명, 실제 재생 확인으로 진행합니다.

다음 연구의 우선순위는 **가시성 판단을 분리한 합성**과 **RIFE 일반·경량 모델 비교**입니다. 신경망은 먼저 버전을 고정한 RIFE 4.25와 경량 모델을 오프라인 비교 도구에 연결합니다. 사용자용 엔진 선택 기능은 그 결과를 확인한 뒤 판단합니다.

신경망 측정에는 원본 전달, 색 변환, 요청한 모든 중간 시점의 추론, D3D11으로의 반환 비용을 포함해야 합니다. 원본 프레임은 신경망 경로 밖에서 그대로 보존합니다. 신경망에서 흐름·마스크만 받아 기존 셰이더로 합성하는 혼합 방식은 별도 후보로 취급합니다. 모델의 마지막 영상 재구성 단계를 생략하면 품질이 달라질 수 있기 때문입니다.

입력 속도를 S, 출력 속도를 T라고 하면 초당 처리량은 대략 다음 비용으로 구성됩니다.

`S × 프레임 쌍 준비 비용 + (T−S) × 중간 프레임 하나의 생성 비용`

24→120에서는 입력 한 쌍당 중간 프레임 4개, 24→240에서는 9개를 생성합니다. 후자의 경우 쌍 준비·디코딩·렌더링·GPU 경합 비용을 전혀 제외해도 중간 프레임 하나에 쓸 수 있는 시간은 최대 약 4.63ms입니다. 이는 처리 예산 계산이며 엔진의 실측 속도가 아닙니다. 중간 프레임 하나만 만드는 시험의 속도만으로 엔진을 선택하지 않습니다.
